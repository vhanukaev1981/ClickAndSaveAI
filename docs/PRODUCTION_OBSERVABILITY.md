# ClickAndSaveAI Production Observability

## Truth State

Structured operational logging: `REPOSITORY_READY` after backend tests pass on the exact candidate SHA.

Monitoring specification: `SPECIFIED_NOT_ACTIVE`.

Notification channels: `OWNER_ACTION_REQUIRED`.

Production monitoring verification: `PRODUCTION_VERIFICATION_REQUIRED`.

**LOG EXISTS does not mean MONITORING READY. METRIC SPECIFIED does not mean ALERT ACTIVE.**

## Structured Operational Envelope

Backend operational events use `functions/src/operationalTelemetry.js` with canonical fields:

- `schemaVersion`
- `event`
- `subsystem`
- `outcome`
- `severity`
- `code`
- optional `correlationId`
- optional pseudonymous `actorRef`
- bounded sanitized `details`

The helper filters secret-bearing/directly identifying detail keys, request bodies/headers, and bounds nested payload size. Product/business return values remain authoritative; the log envelope is operational evidence only.

## Required Monitoring Coverage

The canonical specification is `operations/monitoring/monitoring-spec.json` and covers:

- Gmail OAuth connection and disconnect/provider-cleanup retry;
- Gmail watch/incremental processing and reconciliation degradation;
- push delivery failures;
- provider handoff queue failures;
- imported-data/account deletion failures or retry-required states;
- production deployment/recovery control-plane failures.

## Activation Requirements

Before any metric can be reported as active production monitoring, the owner must create and verify the corresponding resources in the production environment:

1. log routing/query/filter against the real production project;
2. log-based metric or control-plane metric;
3. alert policy with the reviewed threshold/window;
4. notification channel and routing destination;
5. IAM required to read/create/manage those resources;
6. a controlled test showing the alert fires and reaches the intended recipient;
7. an evidence record tying the active resource IDs to the monitoring specification version.

Until those steps are complete, the metric remains `SPECIFIED_NOT_ACTIVE` even if matching logs already exist.

## Privacy Rules

Operational telemetry must not include:

- access/refresh/authorization tokens or codes;
- secrets, passwords, API keys, private/encryption keys;
- request bodies or authorization headers;
- raw email addresses;
- Gmail body/attachment content;
- unnecessary direct user identifiers.

Where actor association is operationally necessary, use the deterministic pseudonymous `actorRef` generated by the telemetry helper.

## Deployment and Recovery Monitoring

Deployment/recovery monitoring is a control-plane concern. Repository CI can validate workflows/specifications, but active production alerts require real GitHub/GCP/Firebase production identities and resource bindings. Failed production deployment/recovery workflows should be surfaced through the canonical `deployment.workflow.failure` and `recovery.workflow.failure` monitoring concepts once the production control plane is created.

## Verification Evidence

A future production activation record should preserve:

- production project/environment identity;
- metric IDs and filters;
- alert policy IDs;
- notification channel IDs (not secret values);
- test event time and resulting alert/notification evidence;
- specification version and source SHA;
- owner approval.
