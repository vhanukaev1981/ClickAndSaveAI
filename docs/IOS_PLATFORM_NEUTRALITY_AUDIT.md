## 1. Executive Summary

Click & Save AI uses Firebase as its canonical backend authority. The Android application is an edge client; all financial calculations, savings opportunity matching, recurring invoice classification, provider lead generation, and account privacy lifecycles reside authoritatively in Cloud Functions and Firestore.

This audit conducted a full codebase inspection of `functions/src/`, Firestore collection models, authentication flows, push notification delivery pipelines, and App Check security enforcement to determine whether the backend can support a native iOS application alongside Android without architectural drift or breaking changes.

### Key Audit Findings:
1. **Push Contract Decoupled**: `registerPushToken` previously hardcoded `platform: "android"`. It has now been hardened in `functions/src/pushFunctions.js` to accept `platform: "android" | "ios"`, defaulting safely to `"android"` for backwards compatibility. `sendPushToUser` now delivers both `android` and `apns` payloads via Firebase Cloud Messaging multicast.
2. **Strict App Check Enforcement**: All 24 client-facing callable Cloud Functions enforce Firebase App Check (`enforceAppCheck: true`). The iOS client must implement App Check using `DeviceCheck` and `AppAttest` in production, and `AppCheckDebugProvider` in development.
3. **Gmail Readonly OAuth Compatibility**: The Gmail connection flow (`connectGmail`) exchanges an offline `serverAuthCode` against the Google Web OAuth Client ID (`googleOAuthClientId`). Google Sign-In on iOS natively supports requesting a server auth code for a Web client ID with `gmail.readonly` scope. Verdict: `COMPATIBLE_WITH_CLIENT_CONFIGURATION` with zero backend changes required.
4. **Data Model Neutrality**: Firestore collections and documents use strictly standard JSON types (strings, numbers, booleans, timestamps, nested maps). There are no serialized Java/Kotlin objects, platform-specific parcelables, or Android-only schema restrictions.
5. **No Client Calculations**: All savings potentials, VAT inclusions, recurring cost trends, and financial health scores are calculated exclusively on the backend. The iOS app must strictly consume projection models without client-side financial math.

## 3. Firestore Data Model Platform Neutrality Assessment

The Firestore database topology consists of top-level collections and user-scoped subcollections.

### User Subcollections (`users/{uid}/...`):
- `users/{uid}/pushTokens/{tokenId}`:
  - Fields: `token` (string), `platform` (`"android"` | `"ios"`), `enabled` (boolean), `createdAt` (timestamp), `updatedAt` (timestamp).
  - Assessment: **100% Platform Neutral**. Document ID is the SHA-256 hash of the FCM token, avoiding collision across devices.
- `users/{uid}/invoices/{invoiceId}`:
  - Fields: `companyName`, `category`, `amount`, `currency`, `date`, `billingPeriod`, `pdfAttachmentId`, `confidenceScore`.
  - Assessment: **100% Platform Neutral**. Currency values are ISO (`ILS`), dates are ISO 8601 or server timestamps.
- `users/{uid}/opportunities/{opportunityId}`:
  - Fields: `providerName`, `category`, `currentMonthlyCost`, `potentialMonthlySaving`, `potentialAnnualSaving`, `matchedOffer`, `status`, `expiresAt`.
  - Assessment: **100% Platform Neutral**. Pre-computed financial metrics; iOS should display without local calculation.
- `users/{uid}/gmailConnection/status`:
  - Fields: `connected`, `email`, `scopes`, `consentVersion`, `lastSyncedAt`, `syncState`.
  - Assessment: **100% Platform Neutral**. Contains no Android-specific auth states.

### Top-Level Collections:
- `providerOffers`: Read-only public catalog of verified market deals.
- `providerLeads`: Attribution leads created when users accept savings opportunities.
- `financialActivityLedger`: Append-only event history for user activity screen.

## 4. Auth & OAuth Platform Considerations

1. **Firebase Authentication**:
   - iOS client uses `FirebaseAuth` SDK. Supports Email/Password and Google Sign-In credential providers seamlessly.
   - User identity UID is identical across Android and iOS for a given account.

2. **Gmail Readonly OAuth**:
   - Required scope: `https://www.googleapis.com/auth/gmail.readonly` (strictly read-only; never request write/modify scopes).
   - Google Sign-In SDK on iOS (`GoogleSignIn-Swift`) supports offline server auth code exchange:
     ```swift
     GIDSignIn.sharedInstance.configuration = GIDConfiguration(
       clientID: iosClientId,
       serverClientID: webClientId
     )
     ```
   - When the user taps "Connect Gmail", request the `gmail.readonly` scope.
   - The returned `user.serverAuthCode` is passed directly to the `connectGmail` callable.
   - The backend exchanges `serverAuthCode` with Google's token endpoint using `client_id: webClientId` and `redirect_uri: ""`. Because this is the standard Web server auth code grant, Google's token endpoint validates it identically regardless of whether the request originated from Android or iOS.

## 5. Push Notification Platform Readiness

1. **Multicast Notification Format**:
   - `functions/src/pushFunctions.js` delivers via `getMessaging().sendEachForMulticast()`.
   - The payload contains:
     - Root `notification: { title, body }`
     - Root `data: { type, sourceMessageId?, opportunityId?, offerId? }`
     - Platform-specific `android: { priority: "high", notification: { channelId: "savings_opportunities" } }`
     - Platform-specific `apns: { payload: { aps: { sound: "default" } } }`
2. **Device Registration**:
   - On iOS, `FirebaseMessaging` produces an FCM registration token once APNs device token is received.
   - iOS client calls `registerPushToken({ token: fcmToken, platform: "ios" })`.
3. **Sign-Out Revocation Gate**:
   - Crucial architectural requirement: Sign-out on iOS MUST call `unregisterPushToken({ token: currentToken })` and await its result BEFORE calling `FirebaseAuth.signOut()`.
   - If `unregisterPushToken` fails or times out, fail-close and do NOT complete sign-out (mirrors Android P0 safety contract).

## 6. Recommendations for Claude Code (Native iOS Implementation)

1. **Language & Architecture**:
   - Swift 6 / 5.10 with SwiftUI and `Observation` framework (`@Observable`).
   - Repository pattern mirroring Android: `AuthRepository`, `GmailRepository`, `FinancialHomeRepository`, `OpportunityRepository`.
2. **App Check Setup**:
   - In `AppDelegate` / app entry point:
     ```swift
     #if DEBUG
     let providerFactory = AppCheckDebugProviderFactory()
     #else
     let providerFactory = AppAttestProviderFactory()
     #endif
     AppCheck.setAppCheckProviderFactory(providerFactory)
     ```
3. **Localization**:
   - Default language: Hebrew (`he-IL`). All UI strings must match Android Hebrew copy for brand and product consistency.
   - Right-to-left (RTL) layout support must be native and verified.
4. **Push Routing**:
   - Handle notification payload in `userNotificationCenter(_:didReceive:withCompletionHandler:)`.
   - Route to exact entity views (`PushTargetView`) using `sourceMessageId` (for invoices) or `opportunityId` / `offerId` (for savings opportunities).
   - Ignore entity notifications that lack exact target identifiers.
